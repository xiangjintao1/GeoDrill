钻探问答项目：从第一步到做出结果

这一次先学“怎么把项目做出来”，暂时不读几百行源码。

我们始终只用一个例子：把一份钻探案例放进系统，然后问——“绿色钻探示范项目采用了什么钻头？”

学完后，你应该能说清楚：资料从哪里来、程序怎样处理、数据存在哪里、模型做了什么，以及每一步怎样确认成功。

先用一分钟看懂最终要做什么

假设老师给你一份资料，里面写着：

项目配套采用长寿命表孕镶金刚石钻头等钻具，并优化钻具组合与钻进参数。

这句话来自项目现有的教学案例摘要。现在你想做一个程序：用户不用自己翻资料，输入问题，程序就找到这句话并回答。

最终效果应该接近下面这样。这是目标示意，还不是已经跑通的真实问答结果。

用户：绿色钻探示范项目采用了什么钻头？

系统：案例采用了长寿命表孕镶金刚石钻头。
      依据：该案例资料中关于钻头与配套工艺的原文片段。

要做到这件事，可以拆成两次工作：

第一次：准备资料，建立可查询的知识库。
    文件 → 程序读取 → 提取知识、计算向量 → 存入知识库

以后每次：接收问题，从知识库找依据，再回答。
    问题 → 找资料/查关系 → 整理回答 → 附上依据

第一条叫“建库”，第二条叫“问答”。问答之前，要先有能查到的资料。

你现在到底处在哪一步

我们已经把项目的“程序骨架”准备好了，但尚未完成一次连接真实服务的建库和问答。

已完成 还要完成
下载原项目 开启电脑虚拟化、重启并启动 Docker 引擎
新增钻探领域代码和配置 启动 OpenSPG，创建钻探项目
准备两份教学案例摘要 填入真实的大模型和向量模型配置
安装 Python、Docker、WSL 把资料实际写入知识库
完成部分离线检查 用问题验证答案和引用

这是此前核验到的进度，不代表文档会自动监测电脑状态。

“代码写好了”和“系统能正常回答”是两个里程碑。接下来要做的是把各部分连接起来。

第一站：先确定要做什么，避免一开始什么都想做

开发者此时的任务：写清需求。暂时不写代码。

我们的第一版需求如下：

要决定的事情 第一版的选择
谁来用 学习钻探知识的人
回答什么 钻进工艺与取心、钻头与钻具
依据什么回答 导入的资料
怎么提问 先在终端输入一个问题
输出什么 答案和支持它的原文
没资料支持时 明确说明证据不足

你可能会问：为什么先用终端，而不是直接做一个漂亮聊天页面？因为我们要先证明“能从资料找到正确答案”。页面可以等这个流程跑通之后再接。

这一站完成的标志：你能拿出一个具体问题，并明确什么回答算合格。

例如，本例的合格答案必须说出“长寿命表孕镶金刚石钻头”，而且引用的资料里确实有这句话。只要答得流畅，并不算通过。

第二站：弄清楚有哪些程序，各自负责什么

开发者此时的任务：画清楚分工，然后选用已有工具。

本项目分成四部分：

部分 它做什么 在哪里运行
我们的 Python 业务程序 接收命令，安排建库和问答 你的 Windows 电脑
OpenSPG 服务 管理知识结构，保存并查询知识 你电脑上的 Docker 容器
对话大模型 阅读资料、抽取知识、理解问题、组织回答 可以是在线模型接口
向量模型 把文字变成便于按意思检索的数字 可以是在线模型接口

“向量”先这样理解就够了：程序不能直接计算两句话的意思有多接近，向量模型把句子转成一串数字，让检索系统能比较相近程度。

本地部署并不要求把大模型也装到本机。 本机可以运行程序和知识库，再通过网络调用模型。

用软件工程的语言说，我们复用了一个框架：KAG 已经写好了很多读取、抽取、检索的通用功能，我们主要补钻探领域的规则和调度入口。

第一版的连接关系是：

你的终端命令
       ↓
我们的 Python 程序
       ├──请求模型：帮忙理解、抽取、生成
       └──请求 OpenSPG：帮忙保存、查询

这一站完成的标志：你知道模型不是数据库，OpenSPG 也不是大模型。

第三站：准备一份资料，先把输入做小

开发者此时的任务：选资料、清理资料、保留来源。

第一版直接使用项目现有的 Markdown 文件。Markdown 是普通文本加少量排版符号，例如 # 表示标题；用编辑器或记事本就能看。

下面直接展示本例资料。你不用另外找文件：

# 矿产绿色勘查钻头与钻具案例

来源：中国地质调查局
文章：《探矿工程所集成绿色钻探技术助力新一轮找矿突破战略行动》
发布日期：2025-12-05
来源地址：https://www.cgs.gov.cn/ywdt/dwdt/202512/t20251205_855312.html
资料性质：官方案例的教学摘要，不是完整技术报告。

该绿色钻探示范项目使用模块化岩心钻机，便于快速拆装和搬运。
项目配套采用长寿命表孕镶金刚石钻头等钻具，并优化钻具组合与钻进参数。
报道将这些配套措施与改善硬岩打滑、破碎地层取心困难联系起来。
资料没有提供钻头具体型号、钻具尺寸或参数数值。

它存放在：kag/examples/drilling/examples/corpus/02-bits-tools.md。另一份现有样例是钾盐勘查取心案例。这些样例用于学习流程，尚不足以覆盖钻探专业知识。

为什么要记录来源？以后用户问“你凭什么这么说”，系统需要能回到相应材料。为什么不把所有资料拼成一大段？大文件往往包含多个主题，后续切分和来源定位会更困难。

这一站的输入：原始资料。输出：干净、带来源的文本文件。

第一版先用这些已整理的文件，不必同时学习 PDF 识别、图片 OCR 和表格抽取。等文字流程跑通后，再增加这些读取能力。

第四站：设计“资料整理后长什么样”

开发者此时的任务：定义数据结构。这里才用到 Schema。

先看三件不同的东西：

原始资料：一段文字。
Schema：规定允许记录哪些类别、怎样建立联系。
知识数据：从具体资料里提取出来的对象和联系。

以我们的例子来说，可以把结果整理成：

对象 1：绿色钻探示范项目       类别：工程案例
对象 2：长寿命表孕镶金刚石钻头 类别：钻头

联系：对象 1 —— 使用钻头 —— 对象 2

为了让程序也能表达这些结构，我们在 Schema 中写：

EngineeringCase(工程案例): EntityType
    properties:
        usesBit(使用钻头): DrillBit
            constraint: MultiValue

这四行可以按下面的顺序理解：

  1. 允许存在一类对象，叫“工程案例”。英文名字供程序使用。
  2. 接下来声明它能记录哪些信息。
  3. 它可以通过“使用钻头”关联到一个钻头对象。
  4. 同一个案例可以关联多个钻头。

Schema 没有告诉我们这个项目用了哪一种钻头。那条事实要从资料里来。

当前初版还定义了钻进方法、取心方法、钻具、地层条件、取心质量指标和“其他”等类型。全部放在 Drilling.schema 中。

开发时，你会根据资料和问题修改结构。例如需要精确区分“钻机”和“钻具”，就应补充合适的类型，而不是强行把钻机当作钻具。

这一站的输入：目标问题和少量样本资料。输出：一份能够表达这些资料的结构说明。

第五站：写业务程序，把框架的功能接起来

开发者此时的任务：写调用流程。不是自己重新实现数据库或大模型。

当前业务的几个文件，按“你做什么时改它”来理解：

你在开发什么 对应文件 需要做的修改
定义知识结构 schema/Drilling.schema 增加实体、属性、关系
规定模型怎样抽取和回答 prompts.py 改抽取、标准化、引用规则
选择组件、模型和参数 kag_config.yaml 改连接、切分和检索设置
接收用户命令并调度流程 run.py 改入口、参数、结果保存
检查错误输入有没有被处理 tests/test_cli.py 补充测试用例

这些文件的完整代码在逐行文档里已经提取；现在先看三个关键动作，理解“程序如何把功能串起来”。

动作一：读取资料前，检查文件

当前代码包含下面这段：

files = sorted(directory.rglob("*.md")) if directory.is_dir() else []
if not files:
    raise ValueError(f"没有找到 Markdown 语料：{directory}")

第一行：目录存在，就递归找出所有 .md 文件并排序。第二、三行：一个文件都没找到，就停止并明确报错。

这不是知识抽取，只是在保证输入存在。初学者常把“文件检查成功”当成“已经建好知识库”，这里一定要分清。

动作二：让模型按约定格式抽取

业务提示里直接写着这些要求：

只使用原文明示的信息；保留型号、单位、适用条件，不用背景知识补全描述。
输出 JSON 数组，每项含 name、category、type、description。
没有实体时输出 []。

它想得到的结构大致如下。下面是说明格式的示例，不是实际抽取运行结果：

[
  {
    "name": "长寿命表孕镶金刚石钻头",
    "category": "DrillBit",
    "type": "钻头",
    "description": "该示范项目配套采用的钻头"
  }
]

为什么要让模型输出这种格式？因为程序容易读取 name、category 这些固定字段。随便返回一段聊天文字，后面的图谱写入就很难处理。

模型仍可能抽错、漏抽或输出格式不符。写 Prompt 是提出要求；检查模型结果才是在验证要求是否被遵守。

动作三：调用框架执行完整建库

当前代码中真正启动构建的关键两行是：

chain = KAGBuilderChain.from_config(config["kag_builder_pipeline"]["chain"])
result = await chain.ainvoke(str(path), max_concurrency=2)

第一行：根据配置，把读取器、切分器、抽取器、向量化器和写入器组装起来。

第二行：把一个文件交给组装好的处理链，等待它处理完。await 是“等待异步任务完成”；暂时不必研究事件循环实现，也能看懂这里的业务顺序。

max_concurrency=2 是框架内组件任务的并发限制，不意味着这份文件只会调用两次模型。

这一站的输出：能够调度资料处理和问答的程序。写好它以后，还要接真实服务。

第六站：准备运行环境，让程序真的有地方执行

开发者此时的任务：让解释器、依赖和服务可用。

先解释几个常见词：

词 在这里的含义
Python 解释器 执行 .py 文件的软件
依赖包 项目调用的现成代码，例如读取 YAML 的包
.venv 本项目独立存放解释器和依赖的环境
Docker 运行已经打包好的 OpenSPG 等服务的工具
容器 正在运行的一份服务实例
WSL 2 Windows 上运行这些 Linux 容器所需的基础环境之一

我们此前已安装软件。现在必须先完成虚拟化设置和重启，让 Docker 引擎可以运行。这一步是在准备机器，不是在给项目增加业务功能。

之后的命令在哪里输入

在 Windows 打开 PowerShell，先执行：

Set-Location '你的项目目录'

它表示“把终端当前目录切到项目根目录”。之后本文的命令都在这个目录运行。

先检查 Python：

.venv/Scripts/python.exe --version

应该显示 Python 3.10.x。我们明确指定 .venv 里的解释器，避免不小心用了电脑里另一个版本。你不需要先学习虚拟环境激活命令。

再执行不需要模型或数据库的资料检查：

.venv/Scripts/python.exe kag/examples/drilling/run.py inspect

怎么知道成功？ 它应该列出两份 .md 文件及字符数，最后说“共 2 份语料；仅检查文件，尚未抽取或建库”。

到这里，证明 Python 程序能运行，也找到了资料。还没有建立知识库。

第七站：启动知识库服务，再把模型和项目连接上

开发者此时的任务：联调。也就是让原本分开的程序能相互通信。

这一站分三小步，按顺序做。

7A. 启动 OpenSPG

完成虚拟化、重启并打开 Docker Desktop，等待引擎运行后，在项目根目录执行：

powershell -NoProfile -ExecutionPolicy Bypass -File deploy/local/start.ps1

这个脚本会启动 OpenSPG 和它依赖的存储服务，并检查页面是否可访问。首次可能要下载镜像，因此不会立即完成。

然后在浏览器输入：

http://127.0.0.1:8887

127.0.0.1 就是你当前这台电脑；8887 是这个服务的访问端口。

怎么知道成功？ 页面能打开，脚本报告就绪。仅仅安装了 Docker，或者终端出现几行启动日志，都不能替代这个检查。

上游演示配置的初始账号是 openspg，密码是 openspg@kag。我们尚未完成实际登录验收。进入后需要创建一个命名空间为 Drilling 的项目，并记录它真正的数字 ID。页面具体按钮要以启动后的实际版本为准。

7B. 拿到模型接口信息

需要两套信息：

对话模型要提供 向量模型要提供
接口地址 接口地址
API Key，也就是认证密钥 API Key
实际可用的模型名称 实际可用的模型名称
— 输出向量的维度

这些信息来自你选用的模型服务。本文没有能替你通用使用的账号或模型名。 没有真实信息时，可以继续理解流程，但不能把示例占位文字当成有效配置去建库。

7C. 把连接信息交给 Python 程序

下面的引号内容必须替换成实际值；Drilling 是项目命名空间，数字 ID 则从页面取得。

$env:DRILLING_HOST = "http://127.0.0.1:8887"
$env:DRILLING_PROJECT_ID = "页面显示的实际数字ID"
$env:DRILLING_LLM_URL = "实际对话模型接口地址"
$env:DRILLING_LLM_KEY = "实际对话模型密钥"
$env:DRILLING_LLM_MODEL = "实际对话模型名"
$env:DRILLING_EMBEDDING_URL = "实际向量模型接口地址"
$env:DRILLING_EMBEDDING_KEY = "实际向量模型密钥"
$env:DRILLING_EMBEDDING_MODEL = "实际向量模型名"
$env:DRILLING_EMBEDDING_DIMENSIONS = "实际向量长度"

$env: 表示给当前终端进程设置环境变量。Python 从这个终端启动时，就能读到这些值。关闭终端后，不要假设这些变量自动保留了。

再运行：

.venv/Scripts/python.exe kag/examples/drilling/run.py check

怎么知道成功？ 出现“配置格式检查通过”。但这个命令只检查格式和完整性，不请求模型，也不验证 API Key；真实连接要在后面的操作里验收。

这一站的输出：服务已经运行，程序也知道该连接哪一个项目、哪一个模型。

第八站：真正建立知识库

开发者此时的任务：先提交结构，再导入资料，最后检查导入结果。

8A. 把结构交给 OpenSPG

.venv/Scripts/python.exe kag/examples/drilling/run.py schema

输入是本地的 Drilling.schema，输出是服务端建立或更新后的类型结构。它相当于先告诉资料库：“我们要记录工程案例、钻头，以及它们之间的关联。”

怎么知道成功？ 终端报告同步完成，并且服务端能看到相应领域类型。这个阶段还没有把两份案例变成知识。

8B. 把案例资料处理后写进去

.venv/Scripts/python.exe kag/examples/drilling/run.py build --data kag/examples/drilling/examples/corpus

build 表示建库；--data 后面是“这次要处理哪一个资料目录”。当前这条命令处理的是两份教学案例。

内部发生的事情，按先后顺序看：

顺序 程序做什么 本例中的输入 → 输出
1 读取文字 文件路径 → 文件内容及文本块
2 按需要切分 较长内容 → 若干较小片段
3 调用模型抽取 片段 → 案例、钻头等实体与关系
4 统一名称并整理 实体别名等 → 更统一的图谱数据
5 调用向量模型 可检索文本 → 数值向量
6 写入服务 节点、关系、文本、向量 → OpenSPG 及对应存储

这份案例很短，具体读取器可能按文档结构产生多个片段；不要先假设一个文件永远只对应一条知识。

怎么知道成功？分两层检查。

第一层：程序没有报错，说明这条处理链至少执行到了返回位置。第二层：在服务端核对数据，再用下一站的问题确认能检索到来源。只有第一层，还不能说问答已经可用。

此时的知识可能呈现为这样的联系。仍是帮助理解的结构示意，实际抽取结果需核对：

工程案例：绿色钻探示范项目
       └──使用钻头──→ 长寿命表孕镶金刚石钻头

相应原文片段：项目配套采用长寿命表孕镶金刚石钻头等钻具……

这一站的输出：已经写入并可被检查的资料与知识数据。

第九站：提问，追踪程序怎样找到答案

开发者此时的任务：运行问答，检查答案是否真的来自资料。

执行：

.venv/Scripts/python.exe kag/examples/drilling/run.py ask "绿色钻探示范项目采用了什么钻头？" --output kag/examples/drilling/results/answer.json

命令里的三个部分：

  • ask：这次是问答，不是建库。
  • 引号里的内容：用户问题。
  • --output 后面的路径：把回答和过程保存在哪里。

这一次内部发生的是：

1. 程序收到问题。
2. 规划器判断需要查询哪些内容。
3. 检索组件去知识库找案例关系和相关文字。
4. 找到支持回答的原文片段。
5. 生成器把问题和原文交给大模型组织答案。
6. 程序显示答案，并保存引用及执行记录。

有一个重要区别：最后给模型的，不应只是问题，还应有从你资料里找出的依据。 这就是知识增强问答的基本工作方式。

期望看到的回答接近：

该案例采用了长寿命表孕镶金刚石钻头。[对应原文引用]

这仍是期望示例，不是保证逐字一致的输出。检查时，要去本次保存的结果中确认引用真的支持这句话，而不是只看答案文字。

如果问一个资料里没有的信息呢

再问：“这个钻头的具体型号和钻压是多少？”我们的样例没有给出这些信息，合格回答应说明资料未提供，不能编造。

代码分两种情况：

检索结果 当前处理方式
完全没有可引用原文 最终生成器直接返回证据不足说明
有原文，但原文没有问题所需信息 通过提示规则要求说明不足；实际是否遵守仍需测试

这一站成功的标志：能给出有依据的答案，也能如实说明资料不知道的内容。

第十站：测试、修问题，再做成可展示的项目

开发者此时的任务：判断系统哪里对、哪里错，再针对性修改。

已经写好的 5 项自动测试，主要检查配置覆盖、数字转换、错误配置和空文件处理。运行方式：

.venv/Scripts/python.exe -m unittest discover -s kag/examples/drilling/tests -v

它们此前已通过，但不验证专业答案。专业问答还要另外做验收，例如：

用例 合格表现
问案例用了什么钻头 名称正确，原文引用匹配
问钾盐案例的取心工艺 回到对应案例，不混用另一份资料
问样例没给的型号 说明缺失，不生成一个型号
问一个无关领域问题 不把不相关片段强行当作依据

发现错误之后，要按环节定位：

现象 先检查哪里 可能需要改什么
根本没找到资料 文件是否导入、索引是否存在、检索设置 导入/索引配置
把钻机当成钻具 知识类型是否够用、抽取是否错误 Schema 和抽取 Prompt
实体重复、不同型号混在一起 别名统一规则 标准化 Prompt、数据清洗
原文正确但回答乱说 最后输入的证据和生成规则 回答 Prompt、证据检查
改了代码结果没变化 是否用了缓存或旧运行环境 checkpoint、实际加载版本

别一出问题就把所有代码重写。先找到哪一个环节的输出不对。

什么时候接页面和 API

当终端里的“建库—检索—回答”能够稳定完成，再做下面这些扩展：

先让一个问题答对
    → 增加一组验收问题
    → 封装后端接口，供页面调用
    → 增加提问输入框、答案区、引用区
    → 测试多人使用、超时和失败提示
    → 根据需要部署到服务器

当前钻探业务入口还没有实现专属的文件上传页面、多人 API、登录权限或自动评测系统。仓库有通用服务代码，不等于这些功能已经接到我们的钻探模块。

这就是后续开发计划，不应把“框架里存在一些模块”直接写成“自己的产品已经具备所有功能”。

到这里，再把整个开发流程串起来

从开发者的角度，你做的是：

确定问题
  ↓ 得到：需求和合格答案标准
选择技术
  ↓ 得到：Python + KAG + OpenSPG + 模型的分工
准备资料
  ↓ 得到：干净、带来源的文件
设计结构
  ↓ 得到：钻探 Schema
写业务流程
  ↓ 得到：配置、Prompt、建库和问答入口
联调服务
  ↓ 得到：程序能访问知识库与模型
实际建库
  ↓ 得到：可查询的资料、图谱和向量
测试问答
  ↓ 得到：有证据的结果，以及待修复问题
迭代与展示
  ↓ 得到：更稳定的接口、页面和部署

从程序运行的角度，只有两条主线：

建库：资料 → 处理 → 入库。

问答：问题 → 检索 → 基于依据回答。

前者是“开发和交付一个系统的流程”，后者是“系统运行时处理数据的流程”。前一版文档把这两种流程和源码细节放得太近，初学者容易混在一起；现在先分别掌握，再对照逐行代码。

你此刻只需要记住的三个检查点

  1. 程序能运行：inspect 能找到两份资料。这一步现在就能学习和检查。
  2. 知识能查到：OpenSPG 和模型连接后，资料成功入库，检索确实返回原文。
  3. 回答有依据：答案与原文一致，没有资料时能说明缺失。

理解这三个检查点，比先背完所有类名和配置字段更有助于你独立开发。
