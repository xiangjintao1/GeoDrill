## 1. 这个项目究竟在做什么

目标是：把钻探资料整理成可检索的知识，再根据这些资料回答问题，并让用户看到答案的依据。

想象你问：“绿色钻探示范项目采用了什么钻头？”系统需要先找到对应项目的资料，取出包含钻头名称的原文，再组织回答。原文没有型号时，系统应说明没有相关信息，不能自行补一个型号。

系统需要三类能力：

| 能力 | 对应部件 | 通俗理解 |
|---|---|---|
| 保存和查询知识 | OpenSPG 及其存储依赖 | 有结构、有索引的资料库 |
| 理解文字和生成文字 | 对话大模型 LLM | 阅读、抽取和组织语言的助手 |
| 按语义寻找文字 | 向量模型与向量索引 | 根据意思而非仅靠字面匹配找资料 |

GeoDrill 是钻探领域应用；KAG 提供构建、规划、检索与生成的 Python 框架，OpenSPG 是独立运行的知识服务。项目版权与许可信息见根目录 NOTICE 和 LICENSE。

这个项目不是在训练一个新大模型。把资料抽取成图谱、计算向量、建立索引，通常称为“建库”。模型通过接口读取输入并输出结果，通常称为“推理调用”。二者与更新模型权重的训练不同。

## 2. 小白需要先懂的编程概念

### 2.1 文件、模块、函数和类

一个 `.py` 文件可以作为 Python 模块。`import` 让当前文件使用另一个模块提供的对象。函数把一段操作封装起来；类把状态和相关操作放在一起；对象是类创建出的具体实例。

```python
class Notebook:                     # 定义一个类，描述笔记本能做什么。
    def __init__(self, title):       # 创建对象时初始化它的状态。
        self.title = title          # 将传入标题保存在这个对象上。
    def show(self):                 # 定义对象的方法。
        return self.title           # 将标题交还给调用者。
book = Notebook("钻探学习")          # 创建一个对象。
print(book.show())                  # 调用方法并显示返回值。
```

`self` 表示“当前这个对象”。`return` 返回一个结果；`print` 只负责显示，显示过的内容不会自动成为函数返回值。我们调用 `build()`，不是让 Python 猜测如何建库，而是执行函数里明确写出的流程。

### 2.2 字典、列表、JSON 和 YAML

字典保存“键—值”，例如 `{"model": "某模型"}`；列表保存多个值，例如 `["钻头", "钻具"]`。JSON 是适合交换这些数据的文本格式；YAML 是更便于人工编辑的配置格式。

```python
config = {"project": {"namespace": "Drilling"}}  # 嵌套字典。
name = config["project"]["namespace"]           # 得到字符串 Drilling。
config["project"]["id"] = 12                   # 向项目配置写入一个整数 ID。
```

YAML 的缩进决定所属层级，不要随意改缩进。在本项目里，`type: md_reader` 表示选择一个已经注册的 Markdown 读取组件，不是 Python 内置的数据类型声明。

### 2.3 `async`、`await` 和并发

模型调用和数据库请求经常需要等待网络。`async def` 定义协程函数；`await` 等待某个异步操作完成，并允许事件循环调度其他可运行任务。`asyncio.run(...)` 在命令行入口创建并运行事件循环。

异步不意味着 CPU 运算自动变快，也不意味着完全不等待。代码中 `for path in files` 仍逐文件执行，前一个文件完成后才处理下一个。文件内部通过 KAG 的信号量限制组件任务并发；设置 `max_concurrency=2` 不等于整个系统严格只会有两次模型请求，因为一个组件可能发起多个内部请求。

### 2.4 继承、装饰器与注册表

`class DrillingNER(OpenIENERPrompt)` 表示继承：继续使用父类的初始化和响应解析方法，只替换领域提示模板。`@PromptABC.register("drilling_ner")` 在模块被导入时登记名字；配置里以后写 `type: drilling_ner` 就能找到该类。

因此“文件存在”和“组件已注册”是两件事。`init_runtime()` 必须导入 `kag.examples.drilling.prompts`，这些装饰器才会执行。名字不一致或漏导入，都会造成组件找不到。

## 4. 两条主线：先建库，再问答

```text
建库阶段
Markdown 资料
    → reader：读取文件，形成文档/文本块
    → splitter：拆成便于处理的小块
    → extractor：调用模型抽取实体、关系与别名
    → vectorizer：为可向量检索的内容计算向量
    → post_processor：图谱后处理
    → writer：把图谱数据写入 OpenSPG

问答阶段
用户问题
    → planner：规划任务与依赖
    → executor：执行图谱检索、文本检索等任务
    → context：汇集结果
    → generator：根据原文组织回答
    → answer + reference + trace：答案、引用和过程记录
```

建库通常在资料更新时执行；问答则随用户提问执行。每次提问都重新遍历 PDF 并抽取全库，会大幅增加等待和调用量，因此系统把二者分开。

### 4.1 用一条资料走通概念

以下只是解释数据结构的示意，不表示我们已经运行抽取服务：

```text
资料：该绿色钻探示范项目使用模块化岩心钻机，配套采用长寿命表孕镶金刚石钻头。

实体：
  工程案例：该绿色钻探示范项目
  钻头：长寿命表孕镶金刚石钻头

关系：
  该绿色钻探示范项目 --usesBit--> 长寿命表孕镶金刚石钻头
```

当前 Schema 没有单独的“钻机”类型。抽取器不应仅凭名字把所有钻机强行归为 `DrillingTool`；可以暂放 `Others`，或由后续版本增加明确的 `DrillingRig` 类型。这正是需要先试抽取、再修订 Schema 的原因。

本例资料中的原始出处、时间与限制条件也要保留。代码会将实体连到来源 Chunk；回答引用的是检索到的原文片段。把 URL 写在文件开头，不自动保证每一个切分后的片段都携带它；真实建库时仍需核验片段的来源元信息。

## 5. 从启动命令到 `main()`

```powershell
.venv/Scripts/python.exe kag/examples/drilling/run.py inspect
```

解释：使用项目的 Python 解释器，执行指定文件，传入子命令 `inspect`。文件末尾的 `if __name__ == "__main__"` 只在直接运行该文件时成立；随后 `main()` 负责解析参数与分派任务。

五个子命令的实际边界如下：

| 命令 | 做什么 | 会访问模型/服务吗 |
|---|---|---|
| `inspect` | 检查 Markdown 文件存在且非空，统计字符数 | 不会 |
| `check` | 检查配置完整性、地址格式、整数参数、命名空间 | 不会 |
| `schema` | 向目标项目同步领域和索引 Schema | 会访问 OpenSPG |
| `build` | 抽取、向量化、写入图谱 | 会调用模型和 OpenSPG |
| `ask` | 规划、检索、生成答案，可保存过程 JSON | 会调用模型和 OpenSPG |

`inspect` 在配置加载之前返回，所以没有密钥也能学习文件处理。`check` 通过不能证明服务可访问、密钥有效或模型存在。

`--config` 属于主解析器，按当前代码应放在子命令前；`--data` 属于 `inspect` 或 `build`；`--output` 属于 `ask`。例如：

```powershell
.venv/Scripts/python.exe kag/examples/drilling/run.py --config kag/examples/drilling/kag_config.local.yaml check
.venv/Scripts/python.exe kag/examples/drilling/run.py build --data kag/examples/drilling/examples/corpus
.venv/Scripts/python.exe kag/examples/drilling/run.py ask "示范项目采用了什么钻头？" --output kag/examples/drilling/results/answer.json
```

前一条自定义配置命令仅展示参数位置，文件需自行准备；后两条只有在模型、服务和知识库准备好后才能成功。程序返回 `0` 表示本次命令正常结束，返回 `2` 表示被捕获的输入、文件或导入错误。其他异常没有被统一捕获，可能直接显示 traceback，这不是完善的生产级异常处理系统。

## 6. 配置是如何变成组件的

`load_config()` 先将 YAML 读为字典，再用 `DRILLING_*` 环境变量覆盖连接字段，最后把 checkpoint 路径固定到钻探模块目录。环境变量不会被这个函数写回 YAML；关闭终端后，本次进程级变量通常不会成为永久配置。

| 环境变量 | 覆盖位置 | 含义 |
|---|---|---|
| `DRILLING_HOST` | `project.host_addr` | OpenSPG 服务地址 |
| `DRILLING_PROJECT_ID` | `project.id` | 已创建的项目 ID |
| `DRILLING_LLM_URL` | `openie_llm.base_url` | 对话模型接口地址 |
| `DRILLING_LLM_KEY` | `openie_llm.api_key` | 对话模型密钥 |
| `DRILLING_LLM_MODEL` | `openie_llm.model` | 服务实际提供的模型名 |
| `DRILLING_EMBEDDING_URL` | `vectorize_model.base_url` | 向量模型接口地址 |
| `DRILLING_EMBEDDING_KEY` | `vectorize_model.api_key` | 向量模型密钥 |
| `DRILLING_EMBEDDING_MODEL` | `vectorize_model.model` | 向量模型名 |
| `DRILLING_EMBEDDING_DIMENSIONS` | `vectorize_model.vector_dimensions` | 向量长度 |

### 6.1 为什么覆盖一处，其他地方也变了

YAML 中 `&llm` 定义一个锚点，`*llm` 引用它。`safe_load()` 会保留对象别名关系。当前 `openie_llm`、`chat_llm` 和流水线里的 `llm` 引用的是同一个字典，所以更新 `openie_llm.model` 后，其余引用也能看到新值。测试专门检查了这个行为。

这也有取舍：配置短、修改集中，但如果你希望抽取模型与问答模型不同，就要拆成两个独立配置；仅修改一个别名引用可能同时影响其他位置。

### 6.2 为什么要显式初始化

`kag` 包在被导入时会自动初始化配置。若进程残留旧生物项目的 `KAG_PROJECT_ID` 和服务地址，就可能加载错误的远程配置。我们的入口先清除旧变量，定位仓库和项目目录，再加载框架、注入本次配置并登记钻探组件。它会改变当前进程的工作目录、模块搜索路径和环境变量；这适合独立命令行进程，不宜不加隔离地嵌入多用户 Web 服务。

另外，原框架读取配置曾依赖系统默认编码，Windows 下可能按 GBK 解释 UTF-8 中文而报错。本地部署时已将两处配置读取改为显式 `encoding="utf-8"`。

## 7. Schema：先设计知识的结构

Schema 不是具体知识，也不是提示词。它规定能有哪些对象、属性和关联方式。当前包含 8 类：钻进方法、取心方法、钻头、钻具、地层条件、取心质量指标、工程案例和兜底的其他类型。

```text
DrillingMethod(钻进方法): EntityType
    properties:
        usesBit(使用钻头): DrillBit
            constraint: MultiValue
```

逐项理解：`DrillingMethod` 是程序使用的英文类型名，括号内是中文显示名；`EntityType` 表示实体类型；`usesBit` 的对象是一个 `DrillBit` 实体，因此这条属性可以表达关联；`MultiValue` 表示一个主体可以对应多个值。

`desc: Text` 是描述文本；`TextAndVector` 表明期望支持文本和向量索引。它不表示在本地 Schema 文件里已经生成了向量，也不表示服务端索引已经可用。

`namespace Drilling` 是命名空间，类似一套类型名称的前缀。它应与服务端创建的项目和配置一致。项目 ID 选错，即使地址和密钥都对，也可能写到别的项目。

`commit_schema()` 除了读取自己的 8 类领域类型，还合并 KAG 索引管理器的内置类型，因此服务端出现 Chunk、Doc 等类型是正常现象。函数不是只在本地检查格式，而是会同步服务端结构。

这份 Schema 是初版设计。例如不同岩层条件的精细分类、带条件的适用性、钻机类型和实测参数还没有完整建模；不能仅凭存在 Schema 就宣称已经有专业、完整的钻探本体。

## 8. Prompt：告诉模型怎样读资料

领域提示分四类：

| 类 | 输入 | 期望输出 | 关键限制 |
|---|---|---|---|
| `DrillingNER` | 原文、服务端 Schema 类别 | 实体数组 | 类别名来自 Schema，描述仅依据原文 |
| `DrillingStandardization` | 原文、实体列表 | 保留原名并补充规范名 | 不同型号不能随意合并 |
| `DrillingTriples` | 原文、实体列表 | 三元组数组 | 保留否定和适用条件，只用约定谓词 |
| `DrillingAnswer` | 问题、任务上下文、引用原文 | 自然语言回答及引用标记 | 不用任务中的猜测替代原文证据 |

`$input` 等是 `string.Template` 模板变量。`OpenIENERPrompt` 的父类初始化会向服务端读取 Schema，填入 `$schema`；调用时再填入本次原文。因此仅创建某些 Prompt 对象也可能需要服务可访问。

### 8.1 模型输出为何要规定 JSON

自然语言“我识别了一个钻头”不好直接写入图谱。固定结构便于程序解析：

```json
[{"name":"示例钻头","category":"DrillBit","type":"钻头","description":"原文支持的描述"}]
```

这是格式示意，不是来自示例语料的真实抽取结果。父类的解析器处理模型返回的数据。提示词要求 JSON，不保证模型必定产生合法、正确的数据；解析成功也不保证事实正确。

### 8.2 为什么谓词写成下划线

当前 KAG 的关系转换会先小写化并清理符号，再把词拼成驼峰。直接输出 `usesCoringMethod` 可能失去大小写边界。我们让模型输出 `uses_coring_method`，框架转换后得到 Schema 中的 `usesCoringMethod`。

`schema_free_extractor` 也会读取服务端 Schema；“free”不能理解成完全没有 Schema。当前它用 Schema 辅助类别识别，关系仍主要靠开放式抽取和提示约束，不能视作严格的关系类型校验器。

### 8.3 无证据是怎样处理的

`DrillingGenerator` 继承通用生成器，覆写 `generate_answer()`：当 `refer_data` 为空时直接返回固定的证据不足说明，不再执行最终回答的模型调用；有引用时调用父类逻辑。

注意三个边界：一是规划、检索等更早阶段可能已经调用模型；二是有引用不等于引用支持答案；三是“有引用但与问题无关”依然要依赖提示约束和验收，当前没有完整的自动证据蕴含检查。

`enable_ref: true` 时，父生成器依据 `biz_scene: drilling` 查找 `drilling_refer_generator_prompt`。所以登记名和场景前缀必须一致，不能只修改 YAML 中的显示名称。

## 9. 一份资料如何真正进入知识库

`build()` 从配置创建 `KAGBuilderChain` 对象，然后逐个文件调用 `chain.ainvoke()`。`DefaultUnstructuredBuilderChain.build()` 用 `>>` 把组件连成有向图。这里的 `>>` 是框架重载的运算符，表示连接处理步骤，不是普通数字的右移用途。

异步执行器对图做拓扑分组，保证前置步骤完成后再执行后续步骤；同一组可以并发执行。每个节点接收前驱节点的输出，因此“reader 输出什么、splitter 接受什么”需要符合组件接口约定。

文本块通过抽取器后，会得到 `SubGraph`，其中包含节点和边。抽取器还将实体与来源 Chunk 连接。向量化组件根据 Schema 里声明的字段生成向量；写入组件调用 OpenSPG 客户端，将数据传给独立服务。

代码里打印“返回 N 项”，不是说写入了 N 条知识，也不是已证明全部数据正确。结果列表项数、节点数、边数、服务端索引条数是不同概念。要确认建库效果，需要检查服务端数据、抽取样本、向量索引以及实际检索。

checkpoint 是中间结果缓存，可以避免重复执行已经完成的工作，但也可能让旧结果继续被使用。更换模型、Prompt、项目或 Schema 后，不能只看语料路径没变就认定缓存有效；应使用新目录/新项目或在确认后管理缓存。当前代码把目录按钻探模块隔离，没有自动按配置内容生成版本号。

还有一个已读到的上游细节：`SchemaFreeExtractor._invoke()` 的同步路径把三元组结果包成了元组，而异步路径没有该包装。当前业务调用异步构建路径；本文只记录该源码差异，不把它扩大为已经复现、修复了所有上游问题。

## 10. 一个问题如何变成带依据的回答

`ask()` 创建 `TraceLogReporter`，再按配置实例化 `SolverPipelineABC` 对应的静态流水线。它调用 `ainvoke(question, reporter=reporter)`，最后取出回答、状态和过程记录。

静态流水线先让 planner 生成任务，将任务放入 `Context`；再按依赖分组执行。我们配置了混合检索、推理和输出执行器，没有配置数学代码执行器。

当前混合检索包括：

- `kg_cs_open_spg`：实体对齐和精确图谱路径查询。
- `rc_open_spg`：相关文本块检索，内部使用向量检索组件。

图谱路径有助于找明确关系，原文检索有助于找解释性文字。合并器汇总结果，生成器再从检索片段整理引用。当前不是把原生物项目的所有检索器一字不差地复制过来，例如未配置其模糊图谱检索分支。

### 10.1 `top_k` 和阈值不是“准确率”

`top_k: 5` 限定某一层希望保留的候选数量，`score_threshold: 0.65` 是某个检索器的分数门槛。门槛依赖向量模型和检索后端，不能解读成“答案有 65% 正确率”。内外层检索器可能各有默认候选数，所以外层设 5，也不能保证每一个内部请求都只取 5 条。

底层向量检索代码会分别查询 Chunk 的内容与名称向量，再合并去重、按分数整理结果。这个细节说明服务端相关字段的索引必须存在；只创建实体而没有可用索引，仍可能检索不到。

### 10.2 保存的 JSON 包含什么

```json
{
  "question": "用户问题",
  "answer": "模型返回的回答或证据不足说明",
  "status": "报告器给出的状态",
  "trace": {"说明": "实际结构由报告器生成，可能包含检索片段与执行记录"}
}
```

这是结构示意。`status` 不是本代码自行验证出来的事实正确率；`trace` 是调试证据，不代表每一步推理都正确。`--output` 路径会创建父目录；同名文件会被覆盖。没有传这个参数时，入口只显示回答，不主动保存 JSON 文件。

## 11. 模型接入：谁负责抽取，谁负责检索

对话大模型用于抽取、标准化、规划与生成；Embedding 模型将文字映射成数值向量。不能把对话模型名随意填在向量模型位置。

`type: openai` 在这里选择的是 OpenAI 兼容协议客户端，不强制要求服务提供商一定是 OpenAI。是否兼容、是否支持指定模型和参数，要看实际服务。`temperature: 0` 倾向于减少随机性，但不能保证跨服务、跨版本逐字一致，更不能保证知识正确。

向量维度要同时匹配模型输出和服务端索引。例如输出 1024 维，不能只在 YAML 里写 1536 就让它变成 1536 维。构建和查询也应使用一致的向量空间；两个模型维度相同，语义空间也未必相同。

```powershell
$env:DRILLING_HOST = "http://127.0.0.1:8887"
$env:DRILLING_PROJECT_ID = "实际项目ID"
$env:DRILLING_LLM_URL = "实际对话模型接口地址"
$env:DRILLING_LLM_KEY = "实际密钥"
$env:DRILLING_LLM_MODEL = "实际对话模型名"
$env:DRILLING_EMBEDDING_URL = "实际向量模型接口地址"
$env:DRILLING_EMBEDDING_KEY = "实际向量模型密钥"
$env:DRILLING_EMBEDDING_MODEL = "实际向量模型名"
```

这些都是待替换的示例，不是可直接使用的账号。建库的模型成本取决于片段数、原文长度、抽取/标准化/关系调用、重试次数；不能仅按资料文件数量估计费用。无证据时最终生成短路，也不代表本次问题完全没有模型费用。

## 12. 本地部署：把各个程序放到哪里

Python 业务程序在 Windows 的 `.venv` 里运行。Docker Desktop 使用 WSL 2 提供运行 Linux 容器的环境。OpenSPG、MySQL、Neo4j、MinIO 是四个不同服务：

| 服务 | 这份编排的用途 | 如何访问 |
|---|---|---|
| server | OpenSPG 服务及页面 | 本机 `127.0.0.1:8887` |
| mysql | OpenSPG 元数据存储 | 容器网络内访问，无宿主机端口映射 |
| neo4j | 图数据及相关检索后端 | 本机 7474、7687；容器内名称为 neo4j |
| minio | 对象存储 | 本机 9000、9001；容器内名称为 minio |

从 Windows 访问服务可用 `127.0.0.1`；server 容器访问数据库则用 `mysql`、`neo4j` 这些容器服务名。容器内部的 `127.0.0.1` 指容器自身，不是 Windows 或另一个容器。

编排使用镜像摘要固定内容，避免同一个 `latest` 标签以后指向不同镜像。使用命名卷保存数据库数据；`down` 通常移除容器和网络、保留命名卷，不等于清空知识库。不要为了解决普通启动问题随便删除数据卷。

绑定 `127.0.0.1` 表示仅从本机访问，便于本地学习。模板里的默认数据库和页面密码是上游演示配置，不应直接当作公网生产部署配置。

`start.ps1` 先检查 Docker 引擎，再启动容器，最后轮询页面。Docker CLI 安装成功只说明客户端存在；`docker info` 能连上服务端才说明引擎可用。配置校验通过，也不代表容器已运行。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/local/start.ps1
docker compose -f deploy/local/compose.yaml ps
docker compose -f deploy/local/compose.yaml logs --tail 80 server
```

启动脚本先给 Compose 最多 300 秒等待服务状态，之后轮询页面最多 60 轮。每轮可能等待 5 秒 HTTP 超时并休眠 5 秒，因此不能把它简单理解成“整个脚本最多 5 分钟”。首次拉镜像的时间还可能另外增加。

页面初始账号 `openspg`、密码 `openspg@kag` 来自上游演示配置；当前尚未实际登录验收。进入服务后，需新建命名空间为 `Drilling` 的项目，并填写实际项目 ID，再同步 Schema、建库和问答。

当前依赖约束固定 Pydantic 2.10.6 与 pydantic-settings 2.8.1，因为原项目使用的 MCP 1.6 引用了新版 Pydantic 已移除的内部接口。固定这两项不等于锁定了全部依赖版本；完整复现还需要记录完整环境和镜像配置。

## 14. 按症状定位问题

| 症状 | 首先检查 | 为什么 |
|---|---|---|
| 找不到 docker | Docker 安装路径、重新打开终端 | 新安装路径可能未进入旧终端环境 |
| Docker 引擎连接失败 | BIOS 虚拟化、WSL、重启、Docker Desktop 状态 | CLI 和引擎是两部分 |
| 8887 打不开 | 容器状态、server 日志、端口占用 | 容器运行不代表应用已就绪 |
| `ModuleNotFoundError` | 是否使用 `.venv/Scripts/python.exe` | 依赖安装在指定环境里 |
| Pydantic 内部 API 导入失败 | 是否按 constraints 安装 | 原项目 MCP 版本有兼容边界 |
| 配置缺字段 | 对应 DRILLING 环境变量是否设置 | 代码只接受实际非空值，不接受占位符 |
| Schema 类别不一致 | 项目 ID、namespace、是否同步 Schema | 模型读取的是服务端结构 |
| 有数据但检索为空 | 向量模型、维度、索引和字段、阈值 | 保存节点不等于索引已可用 |
| 改 Prompt 后结果不变 | checkpoint 和服务实际加载的代码版本 | 缓存或容器仍可能使用旧实现 |
| 引用存在但答案不对 | 引用内容、上下文、生成 Prompt | “有引用”不等于“引用支持” |

不要遇到问题就先换模型或重建全部数据。先判断故障在哪个阶段，再检查该阶段的输入和输出。

## 15. 三个设计选择与取舍

### 15.1 保留 KAG，在业务层扩展

项目约束是学习完整流程、保留已有资产、先做两个钻探主题。复用框架使领域差异集中在少数文件；代价是需要理解注册表、配置装配和服务端结构。另一条路线是手写一个轻量向量 RAG，代码更直观，但要自行实现很多接口；第三条路线是直接使用托管知识库，运维较少，但内部过程不一定适合学习和定制。

本文没有测试三种路线的延迟、吞吐量或费用，因此不宣称某路线快多少倍。可验证的证据是本业务层确实只定义领域类型、提示模板和调度入口，底层仍由 KAG 提供。

### 15.2 配置驱动与硬编码对象

配置驱动的核心机制是“名字 → 注册类 → 检查构造参数 → 递归创建对象”。优点是换组件不必到处改流程；代价是配置错误经常直到运行时才能被发现。硬编码 `Reader(...)` 更容易单步跟踪，适合很小的脚本；使用依赖注入容器可以集中管理对象，但又增加了概念。

YAML 的 `&llm`/`*llm` 减少重复，但会共享同一个字典，测试已经验证这种共享。不要把它误解成“复制一份模型配置”。

### 15.3 小并发、独立进程与可观测性

逐文件、小并发便于初学者确认每一步发生了什么，代价是大规模吞吐较低。扩大并发要同时考虑供应商限流、内存、重试和成本。当前没有做吞吐基准测试，不能根据 `max_concurrency=2` 推出实际每秒处理多少文档。

值得迁移到其他项目的思路是：把外部调用放在清晰边界，把输入检查放在调用之前，把阶段结果保存下来，把“语法通过”“服务可达”“结果正确”分开验收。它同样适用于客服知识库、设备手册助手、法规检索等软件系统。

## 16. 自学练习与参考答案

**练习 1：没有 API Key，能运行哪个命令？** 答：`inspect`；因为它在加载和验证配置前返回。`check` 通常会报配置缺失。

**练习 2：`usesBit` 是钻头名称吗？** 答：不是，是关系/属性名。具体钻头名称由资料提供。

**练习 3：Prompt 文件已经写好，配置为什么还找不到类？** 答：检查是否导入模块触发装饰器注册，以及注册名是否与配置 `type` 一致。

**练习 4：把向量维度从 1536 改成 1024，就能用另一个模型吗？** 答：还要匹配实际输出、服务端索引和建库时使用的语义空间；已有向量可能需要重建。

**练习 5：无引用分支直接返回，为什么仍可能产生模型费用？** 答：最终生成前的规划、抽取或检索辅助步骤可能已经调用过模型。

**练习 6：这是否可以叫 Agent？** 答：它具备规划、工具调用、上下文与生成环节，可以称为采用固定工作流的知识问答 Agent；不是没有边界、能自行执行任意任务的系统。

建议的学习顺序是：能解释 `inspect` → 看懂配置覆盖 → 设计一个 Schema 实体 → 理解注册表和 Prompt → 跑通一份资料 → 检查一次问答证据 → 最后再扩展 API 和页面。本文已经提供各阶段代码，不需要先通读整个上游仓库。
